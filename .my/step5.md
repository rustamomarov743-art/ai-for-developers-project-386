Проектирование бронирования

Основная функциональность проекта это запись на звонок: типы встреч, календарь свободных слотов, бронирование и список встреч владельца. Работы здесь на несколько сессий, и большинство решений ещё не принято, поэтому проектируем её картой решений.

Начните с /wayfinder. Скилл заводит в трекере карту: одну задачу, к которой прицеплены дочерние задачи. Каждая такая задача это вопрос, ответ на который надо принять до реализации: какие сущности есть в контракте, как устроена модель слотов, что происходит при конфликте между разными типами встреч, на каких границах проверять приложение тестами. Карта разбирается по одной задаче за сессию, и несколько заходов это нормальный ход работы.

Пункт назначения карты должен вести к согласованной спецификации приложения, по которой можно создавать тикеты. Своими словами назовите этот результат. Буквальное совпадение с примером не требуется, важно сохранить границы задачи.
Design First и контракт

Этот раздел объясняет, зачем приложению контракт и как из него получается код. На этом шаге вы готовите спецификацию и тикеты. Генерацию контракта и SDK вы настроите в первом тикете следующего шага «Реализация».

Приложение делается в подходе Design First: сначала фиксируем поведение системы и API-контракт, потом реализуем фронтенд и бекенд по нему раздельно. Контракт задаёт границу между частями приложения и остаётся единым источником правды.

Для агентов это даёт конкретный выигрыш: имея явную спецификацию, они не разбирают внутреннюю реализацию соседней части приложения, и расход токенов падает. При изменениях достаточно обновить контракт и синхронно внести правки в обе части.

Контракт описываем в TypeSpec, а OpenAPI-спецификацию из него генерируем. TypeSpec это компактный язык описания API: сущности и эндпоинты записываются коротко и разворачиваются в полноценную OpenAPI. Писать и поддерживать большой OpenAPI руками громоздко, в нём легко ошибиться и разойтись с реальностью.

Посмотрим на простом примере. Опишем тип события и эндпоинт для получения их списка:

```
import "@typespec/http";

using TypeSpec.Http;

model EventType {
  id: string;
  title: string;
  durationMinutes: int32;
}

@route("/event-types")
interface EventTypes {
  @get list(): EventType[];
}
```

После генерации в OpenAPI-спецификации появляется описание маршрута и модели. Ниже показан фрагмент с этими частями.

```openapi generator
paths:
  /event-types:
    get:
      operationId: EventTypes_list
      responses:
        '200':
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/EventType'
components:
  schemas:
    EventType:
      type: object
      required: [id, title, durationMinutes]
      properties:
        id: {type: string}
        title: {type: string}
        durationMinutes: {type: integer, format: int32}
```

Несколько строк описания разворачиваются в подробный контракт. Именно по нему фронтенд и бекенд реализуются независимо друг от друга.

Спецификация это не конечная точка цепочки. Из неё генерируется клиентский SDK для фронтенда: типы запросов и ответов вместе с функциями вызова эндпоинтов. Фронтенд тогда обращается к API через сгенерированный клиент, и часть расхождений обнаруживается при проверке типов ещё до запуска. На бекенде из той же спецификации генерируются свои артефакты (типы, схемы проверки запросов и заготовки маршрутов), если для фреймворка есть генератор. Состав зависит от фреймворка. Если генератора нет, серверную часть пишут по контракту, а совпадение с ним проверяют тесты.

TypeSpec ──> OpenAPI ──┬──> клиентский SDK (фронтенд)
└──> серверные артефакты (если есть генератор)

Генерация обновляет артефакты по контракту. Она не доказывает, что фронтенд использует клиент и что сервер возвращает описанные ответы. Эти свойства проверяются отдельно на следующем шаге. Инструменты генерации выбирайте под свой стек. Команды хранятся в Makefile или в скриптах пакета, чтобы цепочка повторялась одним вызовом.
Что должно уметь приложение

В проекте есть две условные роли: владелец календаря и гости. Регистрации и авторизации нет. Владелец календаря это один заранее заданный профиль, который по умолчанию используется в админской части. Гость бронирует слоты без создания аккаунта и без входа в систему.

Владелец календаря может:

    Создавать типы событий. Для каждого типа события задаёт id, название, описание и длительность в минутах.
    Просматривать страницу предстоящих встреч, где в одном списке показаны бронирования всех типов событий.

Гость:

    Может посмотреть страницу с видами брони, где доступно название, описание и длительность.
    Выбирает тип события, открывает календарь и выбирает свободный слот в ближайшие 14 дней.
    Создаёт бронирование на выбранный слот.

Правило занятости:

    Интервалы двух записей не пересекаются, даже для разных типов событий и одновременных запросов. Например, после брони с 10:00 до 11:00 запись с 10:30 до 11:00 отклоняется. Запись с 11:00 допустима.
    Если гость пытается занять уже занятое время, он видит понятное сообщение о конфликте.

Окно записи по умолчанию:

    Окно записи сдвигается с текущей датой и занимает 14 календарных дней. С какого дня оно начинается, с сегодняшнего или с завтрашнего, решите сами и запишите в спецификацию.
    Слоты формируются в рабочие часы владельца, например с 09:00 до 18:00. Часы работы и часовой пояс, в котором они заданы, тоже записываются в спецификацию.
    Слот длится столько, сколько выбранный тип события. Шаг доступных стартов запишите в спецификации. Он может совпадать с длительностью типа или быть общим для всех типов.
    Гость может записаться только на свободный слот из этого окна.

Внутреннюю реализацию, стек и структуру проекта вы выбираете сами. Здесь мы договариваемся о внешнем поведении системы: какие сценарии поддерживаются, какие данные передаются и какие ограничения действуют при бронировании.
Спецификация и тикеты

Когда решения по карте приняты, соберите их в спецификацию: вызовите /to-spec. Этот скилл интервью не проводит, он синтезирует спецификацию из того, что уже обсуждено, поэтому запускать его надо в сессии, где карта и ответы по её задачам загружены в контекст. Спецификация публикуется в трекер и содержит пользовательские истории, принятые решения по реализации и решения по тестированию: на каких границах приложение проверяется.

Дальше разложите спецификацию на тикеты: /to-tickets. Тикеты получаются вертикальными: каждый проходит через все слои приложения (контракт, сервер, интерфейс, тесты) и проверяется по отдельности. Каждый тикет объявляет, какие тикеты его блокируют, поэтому всегда видно, что можно брать в работу.

Первый тикет реализации должен проверить всю контрактную цепочку на небольшой функции. Например, получение списка типов встреч проходит через TypeSpec, OpenAPI, сгенерированный SDK, сервер и отображение результата на странице. В тикете запишите команды генерации и проверку ответа API. На этом шаге вы готовите постановку и план, код цепочки появится на следующем.

Тикеты, использующие контрактную цепочку, должны зависеть от её настройки. В спецификацию и тикеты включите общую команду проверок, API-тесты, браузерный сценарий, проверку одного теста с временно нарушенным правилом бронирования и настройку release-please после первой функции. На следующем шаге весь граф выполняет /implement-spec.
Требования

    В трекере есть карта решений, её вопросы закрыты с записанными ответами.
    В спецификации описаны роли владельца и гостя, типы встреч, окно 14 дней, рабочие часы, часовой пояс, длительности, шаг стартов, примыкание и конфликты интервалов.
    Спецификация задаёт API и ожидаемые ответы, включая создание бронирования, ошибки данных и конфликт занятого времени. Пути, методы и поля вы выбираете сами.
    Названы границы тестирования, включая прямые запросы к API и браузерный сценарий с настоящим сервером.
    В трекере есть тикеты с зависимостями и ссылками на спецификацию. Первый тикет проводит одну небольшую функцию через контракт, генерацию, сервер, интерфейс и тесты.

Ссылки

Задачи

    Вызовите /wayfinder и заведите карту решений для согласованной спецификации приложения.
    Разбирайте вопросы карты по одному. Записывайте ответы в трекер, учитывая ограничения первого шага. Рассчитывайте на несколько сессий.
    Вызовите /to-spec в сессии, где загружены карта и ответы. Прочитайте полученную спецификацию, проверьте роли, правила времени, API и решения по тестированию.
    Вызовите /to-tickets и проверьте зависимости. У первого тикета должен быть небольшой работающий результат через всю контрактную цепочку. Убедитесь, что граф включает проверки и настройку release-please, затем передайте спецификацию с тикетами в /implement-spec на следующем шаге.

Результат шага

В трекере есть карта с решениями, согласованная спецификация приложения и проверяемые тикеты с зависимостями. Можно начинать реализацию без новых функциональных ограничений.
