# Подготовка к первому шагу без выполнения задания за пользователя

## Context

Пользователь изучает AI-assisted разработку и хочет выполнять шаги самостоятельно. Поэтому помощник не создаёт структуру, не устанавливает навыки и не редактирует проект. Результат — ориентир по файлам из [`getsphericon/sphericon`](https://github.com/getsphericon/sphericon/) и конкретные действия только для первого шага из `.my/step1.md`.

## Approach

Разнести элементы структуры по шагам учебного задания, чтобы пользователь заранее понимал конечную цель, но создавал каждый элемент вовремя и сам. Не переносить прикладной код и инфраструктуру `sphericon`.

## Key changes

Изменений в репозитории помощник не вносит. Пользователю даётся следующая карта.

### Сейчас: шаг 1 — только сценарий приложения

Новые файлы и каталоги создавать не нужно. Пользователь самостоятельно:

1. Изучает сценарий Cal.com или описание и экраны в `.my/step1.md`.
2. Записывает в существующий `README.md` короткий путь владельца: создание типа встречи с названием, описанием и длительностью.
3. Записывает путь гостя: выбор типа встречи → календарь на 14 дней → свободный слот → запись → подтверждение.
4. Добавляет результат: встреча появляется в общем списке владельца; пересекающийся слот повторно забронировать нельзя.
5. Фиксирует ограничения: один владелец, нет регистрации и авторизации, нет интеграций с внешними календарями и уведомлений.

На этом первый шаг заканчивается. `AGENTS.md`, навыки, MCP, Docker и код приложения сейчас не создаются.

### Шаг 2 — каркас и правила для агента

После самостоятельного выбора стека и создания каркаса появятся:

```text
AGENTS.md                  # реальные команды, устройство проекта, Conventional Commits
.mise.toml                 # рекомендуемые версии инструментов и общие задачи
mise.lock
src/                       # frontend, если выбран TypeScript/Vite
server/                    # backend; имя зависит от выбранного фреймворка
tests/
.github/workflows/ci.yml   # общая команда проверок на каждый push
```

`AGENTS.md` лучше получить через `/init` уже после создания каркаса, затем сократить. Существующий `.github/workflows/hexlet-check.yml` не трогать.

### Шаг 3 — навыки и агентная среда

```text
.agents/skills/            # установка через npx skills@latest add mattpocock/skills
skills-lock.json           # создаётся установщиком
docs/agents/
├── issue-tracker.md       # GitHub Issues текущего репозитория
├── triage-labels.md       # пять стандартных меток
└── domain.md              # пути к словарю и ADR
```

Также пользователь добавит в `AGENTS.md` раздел о навыках. Эти файлы настраиваются через `setup-matt-pocock-skills`, а не копируются вручную из `sphericon`.

### Шаг 4 — предметные документы

```text
GLOSSARY.md
docs/adr/
└── 0001-nazvanie-resheniya.md
```

Их содержимое появляется в результате `/grill-with-docs`: словарь фиксирует термины «владелец», «гость», «тип встречи», «слот», «бронирование», а ADR — действительно принятые решения. Заготовки с выдуманными решениями не нужны.

### Шаги 5–6 — контракт, проверки и реализация

После проектирования и выбора генераторов:

```text
typespec/                  # исходный API-контракт
openapi/                   # сгенерированная OpenAPI-спецификация
e2e/                       # браузерный сценарий с настоящим сервером
release-please-config.json
.release-please-manifest.json
.github/workflows/release-please.yml
```

Путь клиентского SDK зависит от генератора. Его и запрет ручного редактирования генерируемых файлов пользователь позже запишет в `AGENTS.md`.

### Шаг 7 — Docker и MCP

```text
Dockerfile
.dockerignore
.mcp.json.example          # либо безопасная проектная конфигурация выбранного агента
docs/agents/mcp.md         # подключение через OAuth или переменные окружения
.env.example               # только если приложению нужны переменные
```

Реальные ключи и сессии в Git не попадают; `.env` уже есть в `.gitignore`.

### Что не нужно копировать из sphericon

Для учебного проекта не требуются его Go/React-каталоги, `ee/`, `charts/`, `fixtures/`, `migrations/`, `Caddyfile`, `compose.yaml`, CLA, Enterprise-лицензии, `CODEOWNERS`, сложные security/nightly workflows и большое количество продуктовых ADR. Полезный ориентир — организация работы агента, а не объём файлов.

## Verification

Помощник ничего не проверяет командами, поскольку не меняет проект. Готовность первого шага пользователь проверяет сам: в `README.md` есть понятные сценарии владельца и гостя, результат бронирования и ограничения приложения; при этом не появился преждевременный код или AI-конфигурация следующих шагов.

## Assumptions

- Пользователь выполняет задание и пишет документы/код совместно со своим агентом самостоятельно.
- Помощник только объясняет назначение файлов и помогает разобраться, если пользователь задаст вопрос по конкретному шагу.
- Стек и агент пока не выбраны; специфические пути не навязываются заранее.
