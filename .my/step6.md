Реализация

Спецификация и тикеты готовы. Вызовите /implement-spec и передайте ссылку на спецификацию в GitHub Issues. Попросите прочитать AGENTS.md, связанные тикеты и их зависимости. Скилл берёт в работу всю спецификацию и собирает реализацию в одной общей ветке.

Тикеты образуют граф зависимостей. Скилл сам выбирает готовые к работе тикеты, запускает исполнителей в отдельных рабочих копиях и объединяет результаты в общей ветке. Независимые задачи могут выполняться параллельно. Настройка контрактной цепочки предшествует задачам, которые её используют.

Исполнители пишут код через цикл TDD и проверяют границы, заданные спецификацией. После выполнения тикетов /implement-spec запускает общее ревью ветки и исправляет его замечания. Если работа сдаётся через pull request, скилл готовит его к ревью. От вас нужно следить за ходом работы, отвечать на вопросы агента и проверить итоговый результат.

Основной сценарий бронирования проверяется в браузере: гость выбирает тип встречи, открывает календарь, занимает свободный слот и видит подтверждение, а владелец видит эту встречу в своём списке. Этот сценарий закрепляется браузерным тестом в репозитории, рекомендуем Playwright. Ручную проверку после следующей правки никто не повторит, а тест запускается одной командой и показывает, что сценарий по-прежнему проходит.

Правила бронирования должны выполняться на сервере. Проверка занятости только в интерфейсе обходится любым другим клиентом: прямой запрос в API создаст вторую запись на то же время.

Обращения к API идут через сгенерированный клиентский SDK. Руками написанный вызов fetch рядом с готовым клиентом уводит фронтенд от контракта, и расхождение всплывает уже на живом приложении. Если контракт по ходу работы меняется, порядок такой: правка TypeSpec, генерация, затем код обеих сторон.

Коммит реализации ссылается на тикет, который он закрывает, например feat: запись на свободный слот (#12). GitHub превращает номер в ссылку, и по истории видно, какой коммит какую задачу делал. До вызова /implement-spec запишите это правило в AGENTS.md рядом с правилом про формат коммитов.
Контрактная цепочка и проверки

Проверьте результат первого тикета. Нужная операция описана в TypeSpec, OpenAPI и клиентский SDK сгенерированы, страница обращается к серверу через клиент. Если фреймворк поддерживает серверный генератор, добавлены его артефакты. Сервер без такого генератора реализован по контракту. Команды всей генерации объединены в один вызов.

В AGENTS.md должны быть названы генерируемые пути и записан запрет править их руками. Если артефакты коммитятся, CI повторяет генерацию и проверяет изменения, включая новые файлы. Если они не коммитятся, CI генерирует их из чистого состояния перед сборкой и тестами. Отдельно проверьте, что обращения фронтенда к контрактному API идут через SDK, а коды и тела ответов настоящего сервера совпадают с контрактом.

Общая команда проверок теперь запускает линтер, проверку типов, API-тесты и браузерный тест. Браузерный тест работает с запущенным приложением, без подмены ответов API бронирования. Один зелёный тест главной страницы из каркаса всего этого не подтверждает.
Проверка теста

В одном из тикетов агент проверяет чувствительность теста к ошибке. Например, в отдельной рабочей копии временно нарушает запрет частичного пересечения разных типов встреч и запускает защищающий тест. Тест должен упасть на проверке соответствующего поведения. Если он остаётся зелёным, агент дополняет тест, затем восстанавливает правильную реализацию и получает зелёный результат. Сломанная версия сервиса не публикуется.

Проверьте, что в тикете сохранены название правила, команда, результаты красного и зелёного запусков и короткое объяснение причины падения.

Настройка release-please тоже входит в граф тикетов и выполняется после первой функции. Агент подключает отдельный workflow, который использует Conventional Commits для подготовки release-PR. Проверьте, что после изменения основной ветки workflow создаёт release-PR.
Требования

    Сквозной сценарий гостя проходится целиком: выбор типа встречи, календарь, запись на свободный слот, подтверждение.
    Одна команда из AGENTS.md запускает все проверки локально и в CI, включая браузерный сценарий с настоящим сервером без подмены ответов API бронирования.
    Занятый слот не предлагается как свободный, повторная запись на это время не проходит, в том числе для другого типа встречи.
    При конфликте слота гость видит понятное сообщение.
    Правила бронирования выполняются на сервере.
    Есть страница владельца со списком предстоящих встреч всех типов.
    В репозитории есть TypeSpec-контракт, OpenAPI и клиентский SDK генерируются одной командой. Серверные артефакты генерируются, если для фреймворка есть подходящий генератор.
    Реализация совпадает с контрактом по путям, методам, полям, успешным ответам и ошибкам данных и конфликта. API-тесты проверяют эти ответы.
    Генерация повторяется в CI. Генерируемые пути и запрет ручных изменений записаны в AGENTS.md.
    Фронтенд обращается к API через сгенерированный клиентский SDK.
    Тесты покрывают основной сценарий бронирования и конфликт слотов, прогон в GitHub Actions зелёный.
    Тест на конфликт проверяет и частичное наложение встреч разной длительности, например встречу на 60 минут в 10:00 и встречу на 30 минут в 10:30.
    Коммиты реализации ссылаются на тикеты, правило записано в AGENTS.md.
    Тикеты спецификации выполнены через /implement-spec, результаты собраны в одной ветке и прошли общее ревью.
    В тикете есть результат проверки одного теста с временно нарушенным правилом и после восстановления.
    release-please подключён и создаёт release-PR.

Ссылки

    release-please подготавливает релизы по Conventional Commits.
    release-please-action запускает release-please в GitHub Actions.
    Playwright MCP: запуск браузерных сценариев и автоматизация пользовательских действий через агента.
    Chrome Devtools MCP: диагностика проблем в браузере, включая сеть, консоль и состояние страницы.

Задачи

    Допишите в AGENTS.md правило, что коммит ссылается на тикет.
    Вызовите /implement-spec со ссылкой на спецификацию и связанные тикеты. Следите за ходом реализации и отвечайте на вопросы агента.
    Проверьте итоговую ветку или pull request, включая контрактную цепочку, общий прогон проверок, браузерный сценарий и результаты эксперимента с тестом.
    Передайте замечания агенту, получите исправления и убедитесь, что GitHub Actions зелёный. После ревью внесите результат общей ветки в основную и проверьте появление release-PR.

Результат шага

Приложение работает по контракту, основной сценарий бронирования проходится и покрыт тестами, включая браузерный.
