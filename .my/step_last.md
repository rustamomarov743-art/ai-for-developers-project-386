Как мы проверяем проект

Автоматическая проверка собирает образ по Dockerfile из корня репозитория, запускает контейнер с переменной PORT=8080 и ждёт, что главная страница ответит кодом 200. Её статус лежит в репозитории на вкладке Actions, в workflow hexlet-check. Подробнее об автоматической проверке можно почитать здесь.

Для проверки в репозитории должны быть два файла, остальная структура остаётся на ваше усмотрение.

```
.
├── .github/
│   └── workflows/
│       └── hexlet-check.yml   # workflow проверки, его создаёт Хекслет
└── Dockerfile                 # по нему проверка собирает образ приложения
```

Контейнер из собранного образа запускает приложение сам, без дополнительных команд. Приложение слушает порт из переменной окружения PORT. Если Dockerfile в корне репозитория нет, проверка падает на сборке с сообщением open Dockerfile: no such file or directory.

Про контракт, бронирования, тесты и трекер автопроверка не знает ничего. Всё это смотрит наставник по четырём зонам ниже.

Ключевой формат работы в проекте: разработку вы ведёте с помощью ИИ-агента. В идеале ни одна строка кода не написана вручную.
Функциональность

    Сценарий записи проходится целиком: тип встречи, календарь, свободный слот, запись, подтверждение.
    Занятый слот повторно не бронируется, в том числе через другой тип встречи, и пользователь видит понятное сообщение о конфликте.
    Правила бронирования выполняются на сервере.
    Есть страница владельца со встречами всех типов в одном списке.
    API отвечает по контракту. OpenAPI-спецификация генерируется из TypeSpec, а из неё клиентский SDK. Серверные артефакты генерируются, если для фреймворка есть генератор.
    Окно записи 14 календарных дней в рабочие часы владельца, начало окна, часы и часовой пояс записаны в спецификации, слот длится столько, сколько выбранный тип встречи.
    Приложение собирается в образ, стартует само и слушает порт из PORT, ссылка на опубликованный сервис лежит в README.md.

Проверяемость

    Тесты и линтер прогоняются в GitHub Actions, прогон на основной ветке зелёный.
    Тесты покрывают сценарий бронирования и конфликт слотов, включая частичное наложение встреч разной длительности.
    Тесты главной страницы из первого цикла запускаются общей командой проверок.
    Одна команда из AGENTS.md запускает все проверки локально и в CI. Браузерный сценарий работает с настоящим сервером, без подмены ответов API бронирования.
    Генерация воспроизводится в CI. Актуальность артефактов, использование SDK и ответы живого сервера проверяются отдельно.
    В тикете есть результат красного и зелёного запусков теста при временном нарушении и восстановлении одного правила бронирования.
    Коммиты идут по Conventional Commits, release-please создаёт release-PR.
    Секретов в репозитории нет.

Настройка агентной разработки

    В корне есть AGENTS.md с командами запуска, тестов и линтера и с правилом про формат коммитов.
    Есть docs/agents/ с конфигурацией трекера и раздел про скиллы в AGENTS.md.
    В репозитории есть проектная конфигурация MCP выбранного агента или безопасный шаблон с инструкцией входа. OAuth и переменные окружения допустимы.

Следы работы по скиллам

    В Issues есть карта решений, её задачи закрыты с записанными ответами.
    В Issues есть спецификация приложения и тикеты с объявленными зависимостями.
    Есть GLOSSARY.md со словарём проекта и записи в docs/adr/.
    Тикеты ссылаются на спецификацию, коммиты реализации ссылаются на тикеты.
    Спецификация реализована через /implement-spec, результаты собраны в одной ветке и прошли общее ревью.

Что дальше

После успешной проверки проект можно развивать как продукт и добавлять новые возможности.

    Гибкое расписание: окна доступности по дням недели, перерывы, исключения и праздничные дни.
    Часовые пояса: хранение зоны владельца календаря и показ слотов для гостей из других регионов.
    Регистрация и аккаунты: несколько пользователей, у каждого свои календари и типы встреч.
    Интеграции с календарями: синхронизация занятости и событий с внешними сервисами.
    Уведомления: напоминания о предстоящих событиях, подтверждения и отмены.
    Дополнительные сценарии: перенос и отмена бронирований, повторяющиеся события, буфер между встречами, аналитика по записям.
